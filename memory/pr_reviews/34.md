## Findings

### F2: A branch push that merges main checks main's merged content  (skipped)

- **severity:** Warning
- **status:** skipped
- **location:** starter/bin/_checks.py:319
- **concern:** A push run on a non-default branch diffs from its `before`, so after merging `main` into the branch it fails on whitespace that `main` already holds, which local checks and the pull request run exclude.
- **resolution:** Only steam-starter runs `bin/check` on pushes to every branch, and its `main` is clean. The case needs whitespace on `main`, which that repository's own push run flags at once, merged into a branch before it is fixed. The next push clears the red check, and the pull request run stays correct. Using the default branch's fork point for such pushes would add payload parsing, a branch, tests, and new push semantics late in the release.

### F1: Cancelled push runs leave their range unchecked  (skipped)

- **severity:** Nit
- **status:** skipped
- **location:** extras/github/.github/workflows/check.yml:15
- **concern:** With `cancel-in-progress: true`, a second push to `main` cancels the first push's run, and the second run starts from its own `before`, so no hosted run checks the first push's whitespace, just as with `[skip ci]` pushes.
- **resolution:** Local `bin/check` already checks unpushed commits since origin's default branch, so the push run is a backstop. The gap needs two code pushes inside one run and whitespace that skipped local checks, and the harm is cosmetic. Closing it needs persisted last-checked state, since GitHub replaces pending runs in a concurrency group even without cancellation.
